# `fedinitcfg.yaml` — federation (multi-cluster)

Available from **NeuVector 5.4.0**. Replaces the manual flow (promote in the UI →
generate a token valid ~1 hour → paste into each remote cluster) with a
declarative join, which is what makes "add a managed cluster" a values-file
change instead of a runbook.

Contains the join token, so it always lives in the **SealedSecret**
`neuvector-init`, never the ConfigMap. Generated by
`scripts/seal.sh fedinit-primary|fedinit-remote`.

## Fields

| field | required | applies to | meaning |
|---|---|---|---|
| `Cluster_Name` | optional | both | Overrides `Cluster_Name` from `sysinitcfg.yaml`. Must be unique across the federation. |
| `Join_Token` | **required** | both | Shared secret binding a remote to its primary. **Exactly 36 characters: a UUID (8-4-4-4-12 hex with four hyphens).** Must be byte-identical on the primary and every remote, or the primary declines the join. Generate with `scripts/seal.sh jointoken`. |
| `Primary_Rest_Info.Server` | **required** | both | Hostname/IP of the primary's fed-master endpoint. The primary needs this too — it is how it advertises itself. |
| `Primary_Rest_Info.Port` | **required** | both | Port of that endpoint. See "Ports" below — with a passthrough Route this is **443**, not 11443. |
| `Managed_Rest_Info.Server` | optional | remote only | Where the primary calls this remote back. |
| `Managed_Rest_Info.Port` | optional | remote only | Port for that callback. |
| `Use_Proxy` | optional | both | `"https"` to route federation traffic through the configured proxy. Empty for us. |
| `Deploy_Repo_Scan_Data` | optional | **primary only** | Sync federated registry scan results down to the remotes. Set `true` on the hub: Harbor is scanned once on the hub and every managed cluster gets the results, instead of every cluster crawling the same registry. |

## Ports — the easy mistake

The Services the chart creates listen on:

| service | port |
|---|---|
| `neuvector-svc-controller-fed-master` | 11443 |
| `neuvector-svc-controller-fed-managed` | 10443 |
| `neuvector-svc-controller-api` | 10443 |

But we expose them through **passthrough OpenShift Routes**, and a Route answers
on the router's **443**. The peer dials the Route, not the Service, so:

```yaml
Primary_Rest_Info:
  Server: neuvector-fed.apps.ocp-qa-hub.x.com
  Port: 443            # NOT 11443
```

Use 11443 / 10443 only if you expose the Services directly (LoadBalancer or
NodePort) instead of via Routes.

## `Managed_Rest_Info` — an upstream contradiction

The upstream documentation describes this field two different ways in the same
page: once as "REST server/port of the `neuvector-svc-controller-fed-managed`
service", and once as "REST server/port of the `neuvector-svc-controller-api`
service".

In practice both Services select the same controller pod on the same port
(10443), so either hostname reaches the same listener. We use the **fed-managed
Route host**, because that Service is the one the chart creates when
`controller.federation.managedsvc.type` is set, and its purpose is unambiguous.

## Examples

Primary (hub):

```yaml
Cluster_Name: qa-hub
Join_Token: 2be93d8f-d42a-44fc-9d33-7c1a6153066b
Primary_Rest_Info:
  Server: neuvector-fed.apps.ocp-qa-hub.x.com
  Port: 443
Deploy_Repo_Scan_Data: true
```

Remote (managed):

```yaml
Cluster_Name: qa-managed-01
Join_Token: 2be93d8f-d42a-44fc-9d33-7c1a6153066b
Primary_Rest_Info:
  Server: neuvector-fed.apps.ocp-qa-hub.x.com
  Port: 443
Managed_Rest_Info:
  Server: neuvector-fed.apps.ocp-qa-mgd01.x.com
  Port: 443
```

## Operational notes

**Clock sync is a hard requirement.** Upstream: "The system clocks (time) must be
the same for each primary and remote cluster." Chrony/NTP drift shows up as a
join that silently never completes.

**TLS is not verified at the transport layer.** `controller/rest/federation.go`
sends federation REST through an HTTP client with `InsecureSkipVerify: true`;
the verifying client is used only for telemetry. Trust comes from the join
token plus the CA/client certificate pair the primary hands the remote during
`/v1/fed/join_internal`, after which NeuVector runs its own mTLS. Consequence:
putting an org-CA certificate on the controller does nothing for federation, so
adding a cluster costs zero CSRs.

**Promotion cannot be done by an SSO admin.** Upstream: "SSO/LDAP/OIDC users with
admin role are not allowed to promote a cluster to primary." Declarative
promotion via this file sidesteps that, but keep the local `admin` account
(`neuvector-bootstrap-secret`) as break-glass.

**Authentication is not federated.** Each cluster keeps its own LDAP/OIDC config
and its own user-to-role mapping. Federation synchronises policy and registry
scan data, not identity.

**What is federated:** federated policy rules pushed primary → remotes, and
registry scan results when `Deploy_Repo_Scan_Data: true`. Dashboards are not
merged; an admin switches cluster context in the hub UI.
