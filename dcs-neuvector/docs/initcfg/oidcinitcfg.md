# `oidcinitcfg.yaml` — OIDC authentication (Keycloak)

Carries the client secret → always in the **SealedSecret** `neuvector-init`.

Planned for the managed clusters (tenant SSO). The hub is admin-only and uses
LDAP instead.

## Fields

| field | required | values | meaning |
|---|---|---|---|
| `always_reload` | optional | bool | Re-apply on every controller start. Set `true` so git owns the mapping. |
| `Issuer` | **required** | URL | OIDC issuer. For Keycloak this ends at the realm: `https://keycloak.x.com/realms/<realm>` — **not** the `.well-known` path. NeuVector performs discovery itself. |
| `Client_ID` | **required** | string | Keycloak client ID. One client per cluster. |
| `Client_Secret` | **required** | string | Client secret. The reason this file is sealed. |
| `Scopes` | optional | list | Default `openid`, `profile`, `email`. Add whatever scope carries the group claim if it is not in the default set. |
| `Group_Claim` / `group_claim` | optional | string | Token claim holding group membership, e.g. `groups` or `roles`. Both spellings appear in the upstream sample; `group_claim` is the one shown in the 5.x examples. Set both if in doubt — matching values are harmless. |
| `Enable` | optional | bool | Turns the auth server on. `false` leaves it configured but inactive. |
| `Default_Role` | optional | `admin` \| `reader` \| `""` | Role for an authenticated user matching no group mapping. **Set this to `""` (none)** — that is what produces "authenticated but permission denied" for a user who is not in any tenant group. Never leave it `admin`. |
| `group_mapped_roles` | optional | list | Group → role mapping, below. |

## `group_mapped_roles`

```yaml
group_mapped_roles:
  # global role, no namespace restriction
  - group: platform-admins
    global_role: admin

  # namespace-scoped only: nothing globally, custom role in named namespaces
  - group: team-alpha
    global_role: ""
    role_domains:
      dcstenant:
        - alpha-app-a1b2
        - alpha-app-c3d4

  # combination: a global role plus extra rights elsewhere
  - group: security-reviewers
    global_role: reader
    role_domains:
      admin:
        - security-tooling-9z8y
```

| key | meaning |
|---|---|
| `group` | Value as it appears in the token's group claim. Exact string match. |
| `global_role` | `admin`, `reader`, `ciops`, a custom role name, or `""`/omitted for no cluster-wide rights. |
| `role_domains` | Map of *role name* → *list of namespaces*. The role may be built-in or one defined in [roleinitcfg.md](roleinitcfg.md). Namespaces are the real Kubernetes namespace names, including our 4-character suffix. |

### Ordering matters

Upstream: "if the user is in multiple groups, the role will be **first matched**
in the order listed." So place the most specific / most privileged mappings
first. A user in both `platform-admins` and `team-alpha` gets whichever appears
earlier in the list — not the union.

This is the single most likely source of a subtle authorization bug once the
list is generated by automation. Whatever generates it must produce a stable,
intentional order.

## Keycloak client settings

| setting | value |
|---|---|
| Client type | Confidential (client authentication on) |
| Valid redirect URI | `https://<manager-route-host>/openId_auth` |
| Base URL | `https://<manager-route-host>` |
| Direct access grants | Disabled |
| Group/role mapper | A dedicated client-scope mapper emitting the group list into the claim named in `group_claim` |

## Two open issues before this can ship

**1. Where do the groups come from?** The intended model is OpenShift groups, but
a token claim can only carry what Keycloak puts in it. NeuVector cannot read
OpenShift `Group` objects (the only native platform-RBAC integration is Rancher
SSO). So either Keycloak gains a mapper backed by the same AD groups that drive
the OpenShift groups, or `Auth_By_Platform` (see
[sysinitcfg.md](sysinitcfg.md)) turns out to do something useful on OpenShift —
which is undocumented at 5.6 and needs a dev test.

**2. Private CA trust.** If Keycloak's certificate is issued by an internal CA
the controller does not trust, OIDC discovery fails. The controller expects the
bundle at `/etc/ssl/certs/ca-certificates.crt` and the chart exposes no value for
it; the upstream workaround is an init container that concatenates the CA onto
the system bundle. A wrapper chart cannot inject that into a subchart
Deployment, so it would need an ArgoCD post-renderer (kustomize patch). Test
early — this is the kind of thing that surfaces on the day of the demo.

Reference: <https://github.com/neuvector/neuvector-helm/issues/542>

## Scale note

With ~200 tenants and ~800 namespaces this list becomes large, and it is a single
YAML document consumed by the controller. Regenerating and re-sealing the whole
file for every onboarding means a controller restart per tenant. The
alternative, and the recommendation, is to keep only the platform/admin groups in
this file and have onboarding call the REST API
(`PATCH /v1/server/<name>` with an updated `group_mapped_roles`) — no restart, and
it fits the existing per-namespace ArgoCD child-chart pattern.
